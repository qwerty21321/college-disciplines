## 1. Выбранный сервис и его форматы сообщений

Я выбрал Telegram, которым пользуюсь для общения. Для разбора взял Telegram Bot API - интерфейс, через который программы работают с ботами.

Bot API возвращает ответы в формате JSON. Запросы идут по HTTPS, параметры можно передавать несколькими способами, в том числе в JSON. Для загрузки файлов используется multipart/form-data.

Этот разбор относится именно к Bot API. Обычные приложения Telegram используют другой протокол - MTProto, поэтому нельзя утверждать, что весь Telegram обменивается данными только в JSON.

## 2. Почему выбран JSON и какие есть альтернативы

JSON подходит для Bot API, потому что его легко читать и обрабатывать. В нём удобно передавать текст сообщения, данные пользователя и вложенные объекты. Библиотеки для JSON есть почти в любом популярном языке программирования. Разработчик может посмотреть ответ сервера и быстро понять, какие поля пришли.

Возможные альтернативы:

| Формат | Почему менее удобен в этом случае |
|---|---|
| XML | Повторяющиеся открывающие и закрывающие теги увеличивают объём обычных сообщений. Для небольших объектов пользователя это лишняя сложность. |
| Protobuf | Требует отдельной схемы и подготовки кода для работы с ней. Ответ нельзя просто открыть как обычный текст. Для общедоступного API это повышает порог входа. |
| YAML | Удобен для конфигураций, но сложнее по синтаксису и чувствителен к отступам. Для обмена небольшими объектами через API JSON проще. |
| MessagePack | Может уменьшить размер данных, но без специальной программы ответ не прочитать. Это усложняет ручную проверку запросов. |

Эти форматы технически можно использовать для похожего API. Однако для Bot API удобство подключения и отладки делает JSON разумным выбором.

## 3. Одни данные в трёх форматах

Возьмём сокращённый профиль пользователя: идентификатор 101, имя Roman, имя пользователя roman41, признак бота false. Это учебные данные, а не реальный ответ с личными сведениями.

### JSON

```json
{
  "id": 101,
  "first_name": "Roman",
  "username": "roman41",
  "is_bot": false
}
```

Для сравнения размера используем запись без пробелов и переносов:

```json
{"id":101,"first_name":"Roman","username":"roman41","is_bot":false}
```

Размер этой строки в UTF-8 - **67 байт**.

### XML

```xml
<user>
  <id>101</id>
  <first_name>Roman</first_name>
  <username>roman41</username>
  <is_bot>false</is_bot>
</user>
```

Та же запись без пробелов между тегами и переносов:

```xml
<user><id>101</id><first_name>Roman</first_name><username>roman41</username><is_bot>false</is_bot></user>
```

Размер этой строки в UTF-8 - **105 байт**. XML-декларация не добавлялась.

### Protocol Buffers: схема

```proto
syntax = "proto3";

message User {
  uint64 id = 1;
  string first_name = 2;
  string username = 3;
  bool is_bot = 4;
}
```

Схема описывает типы полей, а сами значения передаются отдельно в бинарном сообщении. Числа после знака равенства - номера полей, а не значения пользователя.

Если записать те же значения по этой схеме, стандартное кодирование proto3 займёт **18 байт**:

- id: тег поля и значение 101 - 2 байта;
- first_name: тег, длина строки и 5 букв Roman - 7 байт;
- username: тег, длина строки и 7 символов roman41 - 9 байт;
- is_bot: значение false по умолчанию не передаётся.

В шестнадцатеричном виде сообщение выглядит так:

```text
08 65 12 05 52 6f 6d 61 6e 1a 07 72 6f 6d 61 6e 34 31
```

### Сравнение

| Формат | Размер данных | Читаемость |
|---|---:|---|
| JSON без оформления | 67 байт | Понятные названия полей, короткая запись |
| XML без оформления | 105 байт | Структура понятна, но теги делают запись длиннее |
| Protobuf | 18 байт | Для чтения нужна схема и программа-декодер |

Размер схемы .proto не сравнивается напрямую с размером JSON и XML: схема описывает структуру, а не содержит конкретный профиль. В таблице сравниваются сами данные без сжатия, сетевых заголовков и внешней оболочки ответа API. При других значениях и структуре размеры изменятся.

## 4. Что дал бы переход с JSON на Protobuf

Если бы Bot API поддерживал Protobuf, небольшие сообщения могли бы занимать меньше места. В рассмотренном профиле размер уменьшился бы с 67 до 18 байт, примерно на 73%. При большом количестве сообщений это могло бы сократить сетевой трафик.

Схема заранее задаёт типы полей. Можно автоматически получить код для чтения и записи данных. Обработка бинарных сообщений часто быстрее текстового разбора JSON, но реальный выигрыш нужно измерять на конкретной нагрузке.

Ограничения такого перехода:

- разработчикам пришлось бы подключить библиотеки Protobuf и получить схемы;
- вручную смотреть ответы стало бы сложнее;
- пришлось бы следить за совместимостью версий и не использовать заново номера удалённых полей;
- существующие боты нельзя просто переключить на новый формат без обновления их кода;
- экономия на структуре сообщения не уменьшает сами фотографии и видео.

Для большого публичного API JSON удобен своей простотой. Protobuf мог бы быть дополнительным вариантом, но его введение потребовало бы изменений как на сервере, так и у разработчиков ботов. Обычной заменой заголовка запроса перейти на него нельзя.

## 5. Когда XML остаётся оптимальным выбором

XML остаётся разумным выбором в действующей системе обмена документами между предприятиями, если она использует SOAP и согласованные XML-схемы.

Например, складская система отправляет поставщику заказ, а поставщик возвращает подтверждение. У сторон уже есть описание полей, проверка документов по XSD и программы для обработки XML.

В такой системе важны:

- проверка структуры документа по общей схеме;
- совместимость с уже работающими программами;
- пространства имён, позволяющие различать элементы из разных схем;
- сохранение существующего порядка обмена документами.

Переход на JSON потребовал бы менять программы и правила обмена у обеих сторон. Если XML выполняет требования и объём данных допустим, такая переделка не даёт очевидной пользы.
